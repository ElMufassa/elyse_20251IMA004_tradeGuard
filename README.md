## Problem statement
Retail forex trading carries a high risk of loss. Hayley and Marsh (2016) studied almost 100,000 retail FX traders and found that most make losses on average, even experienced ones. Moeeni and Tayebi (2018) list failure to manage risk and lack of discipline among the main reasons traders fail. Many individual traders record trades in notebooks or spreadsheets that enforce no rules, so oversized positions, trades without a stop-loss and trading after heavy losses go unnoticed until the account is damaged.

## Proposed solution
TradeGuard is an Oracle database with PL/SQL business logic that works as a trader's journal and risk gatekeeper. Trades are opened and closed only through stored procedures. Before a trade is accepted, the database checks that it has a stop-loss, that its risk is within the account's limit, that the daily loss limit has not been reached and that the forex market is open. Every rejected or changed trade is written to an audit log, and a dashboard shows performance.

## Objectives
**Main objective:** Design and implement an Oracle PL/SQL database that records forex trades and enforces risk-management rules automatically.

**Specific objectives**
1. Model traders, accounts, currency pairs, price bars, strategies, trades, risk rules and audit records in third normal form (3NF).
2. Load and validate real hourly EUR/USD price data (93,084 rows) into the database.
3. Enforce risk rules with procedures, functions, packages, exceptions and triggers.
4. Record every rejected or changed trade in an audit log.
5. Provide a live Power BI dashboard connected to the Oracle database.

## Data source
- **Primary dataset:** "EUR USD Forex Pair Historical Data (2002-2020)", Oanda hourly bid/ask prices, published on Kaggle (93,084 hourly rows, 12 columns). Mirror page: https://baselight.app/u/kaggle/dataset/imetomi_eur_usd_forex_pair_historical_data_2002_2019
- **Optional second dataset:** "Exchange Rates: Currencies & Gold (2002-2024)" on Kaggle, for additional currency pairs.
- **Personal data:** none. The data is market prices. Trader accounts are pseudonymous.
- **Trade records:** generated by a documented script from real price bars (entry and exit prices come from actual bars) so the database can be demonstrated without any real person's trading history.
- The licence on the Kaggle dataset page will be checked before the data is loaded.

## Innovation
**Option:** Analytics dashboard. **Tool:** Power BI connected live to the Oracle database. It shows win rate, net profit, maximum drawdown, profit by currency pair and month, and rejected trades by rule, with filters. Business rules stay in PL/SQL; Power BI only reads the data. Documentation and screenshots will be in `innovation/`.

## Planned tables (3NF)
| Table | Purpose |
|---|---|
| TRADER | Pseudonymous trader profile |
| TRADING_ACCOUNT | Account balance, status and owner |
| CURRENCY_PAIR | Pair code, pip size, pip value |
| PRICE_BAR | Hourly open/high/low/close per pair |
| STRATEGY | Named trading strategy |
| TRADE | Each trade: side, lots, entry, stop-loss, take-profit, exit, result |
| RISK_RULE | Per-account limits: max risk %, daily loss limit |
| AUDIT_LOG | Who did what, when, and whether it was allowed |

Relationships: a trader has many accounts; an account has many trades and one set of risk rules; each trade belongs to one currency pair and one strategy; each currency pair has many price bars; each audit record refers to a trade.

## Planned PL/SQL features
| Feature | Where it is used |
|---|---|
| Procedures | `open_trade` and `close_trade` record trades and update the account balance |
| Functions | `calc_position_size`, `calc_pips`, `get_win_rate`, `calc_max_drawdown` |
| Cursors | Explicit cursor for the monthly performance report; cursor FOR loop to flag accounts that hit the daily loss limit |
| Packages | `trade_pkg`, `risk_pkg`, `report_pkg` |
| Exceptions | Custom errors: no stop-loss, risk too high, daily loss limit reached, market closed |
| Triggers | BEFORE INSERT on TRADE blocks trades without a stop-loss or above the risk limit; AFTER INSERT/UPDATE/DELETE writes to AUDIT_LOG |
| Restriction rule | No new trades while the forex market is closed at the weekend |
